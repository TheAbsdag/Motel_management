# Persistence Schema — V0.1.5.2

**Date**: September 2026 (code state `287b98b`, release `v0.1.5.2`)
**Version field**: `"version": 3` in every persistence file — **unchanged by this release**
**Purpose**: Document the per-tower pricing default and the room pricing written by a save.
**Releases**: V0.1.5.2

---

## Overview

V0.1.5.2 adds one optional key to `data/applicationProperties` and changes what a save writes
into an existing one. No file, no directory and no migration step is added, and a directory
written by any version since V0.1.4.1 is read as it is.

| File | Change | Compatibility |
|------|--------|---------------|
| `data/applicationProperties` | optional `defaultTimeData` on each tower | Absent in older files → the built-in 3 h / 12 h / 24 h slots are used |
| `data/applicationProperties` | `customTimeData` of a room is now overwritten with the price held by the room grid | none needed, the key already existed |
| every other file | untouched | read and written as in [V0.1.5.1](V0.1.5.1.md) |

---

## 1. `defaultTimeData` — the pricing a new room of a tower starts from

Each entry of `roomsPerTower` may carry the 3 time slots that a room added to that tower is
created with. The floor configuration screen sets them together with the pricing of the rooms
the tower already has (*PRECIOS TORRE*).

```json
"roomsPerTower": [
  {
    "towerNumber": 0,
    "towerFloors": 2,
    "towerRooms": [ { "floor": 0, "rooms": [] } ],
    "defaultTimeData": [
      { "price": 45000, "timeSeconds": 10800 },
      { "price": 50000, "timeSeconds": 43200 },
      { "price": 90000, "timeSeconds": 86400 }
    ]
  }
]
```

- **Absent or empty** → `ProgramConfig.towerDefaultTimeData()` returns
  `ProgramConfig.defaultTimeData()`, the built-in slots of `RoomTime`, so a tower saved before
  this release keeps pricing its new rooms exactly as it did.
- **Present** → used both for the configuration entry of a new room
  (`RoomConfigData.customTimeData`) and for the in-memory room the grid creates, so the room is
  priced the same before and after a restart.
- The key is written by every save of `applicationProperties`; a tower that never had it gets
  `null` until the screen sets a default. Unlike the room list, the value is **not** rebuilt
  from the runtime grid: it is only changed through `ProgramConfig.setTowerDefaultTimeData()`.

## 2. `customTimeData` — the room pricing a save now writes

Every save of `applicationProperties` copies the time slots of each room of the grid into the
matching `roomsPerTower[].towerRooms[].rooms[]` entry (`ProgramConfig.syncRoomTimeData()`,
called from `MotelManagement.saveFilesForMainService()`).

Until V0.1.5.1 that sync only filled rooms whose stored `customTimeData` was `null` or empty.
Every room created by the program already carries the slots it was created with, so a price
changed in the room configuration screen was never copied over: it lived in memory until the
restart, which restored the value from the file. The sync now overwrites the stored slots on
every save, and the runtime room grid is the source of truth for pricing.

- The **names, floor and room numbers** of a room come from the configuration and are written
  back unchanged; only `customTimeData` is taken from the runtime room.
- Rooms of a tower that has more configuration entries than rooms in the grid, or the other way
  round, are matched by index; the surplus keeps its stored value.
- `RoomTime` and `TimeSlotConfig` still hold `price` in COP as `long` and `timeSeconds` in
  seconds, as in every version since V0.1.3.

## 3. Unchanged

`data/roomsInformation`, `data/turn`, `data/inventory`, `data/emailConfig`, the completed turns
in `history/`, the custom layouts in `data/printTemplates/`, the `receiptPrints/` PDFs and the
XLSX / CSV exports behave as described in [V0.1.5.1](V0.1.5.1.md); `"version": 3`,
`ZonedDateTime` in `America/Bogota` and amounts as `long` in COP.
