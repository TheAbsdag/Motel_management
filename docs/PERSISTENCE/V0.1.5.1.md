# Persistence Schema — V0.1.5.1

**Date**: September 2026 (code state `61d3b2a`, release `v0.1.5.1`)
**Version field**: `"version": 3` in every persistence file — **unchanged by this release**
**Purpose**: Document how a data directory written before the version field existed is read.
**Releases**: V0.1.5.1

---

## Overview

V0.1.5.1 adds no field, no file and no migration step for current data: a directory written by V0.1.4.1 or V0.1.5 is read and written exactly as before. It fixes the read path of the files described in [V0.1.2](V0.1.2.md) — no `version` field, durations in hours, 1-based tower numbers — which is the state left on disk by a motel that updates in place from 0.1.2.

Both defects were silent: the program started and showed data that had never been rejected, just converted wrongly.

| File | Defect | Symptom in the program |
|------|--------|------------------------|
| `data/roomsInformation` | The hour-based keys `service` / `extension` had no fallback, so `serviceDuration` came out as `0` | Every occupied room restored already expired, with an extension of 0 |
| `data/turn` | `TurnDetails` started at `version: 3` in memory, and Jackson does not overwrite a property the file omits | The v2 → v3 tower migration never ran: 1-based tower numbers stayed 1-based |

`data/applicationProperties` of that version already loaded correctly and needed no change: `ProgramConfig` reads the version with a `0` default and migrates the tower numbers, and the absent `printerName`, `currencyConfig` and `customTimeData` keys fall back to their defaults (printer unset, default currency, default 3 h / 12 h / 24 h slots).

## 1. `data/roomsInformation` — legacy keys accepted on read

| Key written by 0.1.2 | Key since 0.1.3 | Conversion on read |
|----------------------|-----------------|--------------------|
| `service` (hours) | `serviceDuration` (seconds) | `* 3600` |
| `extension` (hours) | `extensionDuration` (seconds) | `* 3600` |
| `roomString`, `towerNumber`, `floorNumber`, `roomNumber`, `status`, `startStatus`, `endStatus` | same name and meaning | none |

`RoomStateData` prefers the current key whenever it is present, so a file written by this version is never reinterpreted. A field that is missing entirely falls back to `""` for the timestamps, to `FREE` for the status and to the "not found" coordinates, which the restore step logs as a warning instead of failing the start-up.

Two details of that version are kept as they were:

- **`status` 1 / 2 / 3** mean `FREE` / `CLEANING` / `OCCUPIED`, unchanged. For `FREE` and `CLEANING` rooms the timers in the file are ignored and the room is restored with the current time, exactly as for a current file.
- **Rooms are matched by coordinates, never by `roomString`.** A 0.1.2 file whose names look like `1-105` restores onto whatever grid `data/applicationProperties` defines at those tower / floor / room indices; the name shown on screen is the one in the grid, not the one in the state file.

The next save writes the file back in the current format: `serviceDuration` / `extensionDuration` in seconds and `"version": 3`, so the conversion happens once.

## 2. `data/turn` — an absent `version` means legacy

The activity fields were already readable since 0.1.3 (`service`, `extension` and `servicedExtension` in hours convert to seconds, `roomData` is rebuilt from the individual coordinates when absent). What was broken is the **tower migration**: the v2 → v3 step is driven by the `version` field, and a file without one was read as if it were already current.

| `version` in the file | Tower numbers | Reason |
|-----------------------|---------------|--------|
| absent (`0`) | 1-based, migrated to 0-based on load | Predates the version field ([V0.1.2](V0.1.2.md)) |
| `2` | 1-based, migrated to 0-based on load | V0.1.3 — V0.1.4 |
| `3` | 0-based, used as they are | V0.1.4.1 onwards |

The migration decrements the tower of `RoomBookingActivity` and of both sides of `RoomSwapActivity`, including the tower inside their embedded `RoomData`, and leaves every other activity type untouched.

**A file without `version` is therefore always treated as legacy**, which makes the write path part of the contract: `TurnDetails.toJson()` stamps `"version": 3`, so the file written back is current and loading it again does not decrement the towers a second time.

---

## 3. Unchanged

The write format of every file, the four active state files, the completed-turn archives in `history/`, the `data/printTemplates/` layouts and the XLSX / CSV exports behave exactly as described in [V0.1.5](V0.1.5.md); `"version": 3`, `ZonedDateTime` in `America/Bogota` and amounts as `long` in COP.
