# Persistence Schema — V0.1.6.1

**Date**: November 2026 (release `v0.1.6.1`)
**Purpose**: Document the numbering rule applied to `data/applicationProperties` on load.
**Releases**: V0.1.6.1

## Overview

| File | Change | Compatibility |
|------|--------|---------------|
| `data/applicationProperties` | none — same keys, same `"version": 3` | numbers are read, then normalized to their position |
| `data/roomsInformation` | none — same keys, same `"version": 3` | written with the normalized numbers |
| every other file | untouched | read and written as in V0.1.6.0 |

## 1. Numbering rule

`towerNumber`, `towerRooms[i].floor` and `towerRooms[i].rooms[j].roomNumber` are
positions, not labels: after loading, deleting a tower, a floor or a room, they equal
their index in the list. A file stored with a hole (only possible after deleting a
middle element with an older build) is closed up on load.

## 2. Room names

`roomString` is a name. On normalization it is regenerated only when it still equals
`buildRoomString` of its old position (`<tower+1>-<floor+1>0<room+1>`). A name typed by
the operator — `Suite`, `VIP`, a renamed number — is kept as it is.

## 3. State file

`data/roomsInformation` maps each room by those numbers, so the normalization runs
before the room grid is built and before the states are restored. A state file written
by 0.1.6.1 keeps the state of the remaining rooms after a deletion. A file written by
an older version after a deletion can lose it: the entries still carry the numbers the
removed floors or rooms had, so an entry may be dropped as out of range or, when that
number still exists, land on a different room; those rooms start free.
